=== PART 1: shared service layer, terminal parity, review workflow (no browser yet) ===

1. 2. Long actions (report generation, evals, QuickBooks pull) run as background jobs with an id, status, capped log and timeout. One running job per client. The CLI versions stay synchronous.

3. Company creation in two steps, so a human approves before anything goes live:
   - init-client gets --draft: it writes data/clients/<id>/draft/config.yaml plus draft_summary.json (detected sheet and rows, check results such as 65/65, warnings). Plain init-client keeps its current behaviour.
   - New validate-config --client <id> [--draft] reuses the existing config loader (add only if no such command exists).
   - New approve-config --client <id> --by "<name>": re-validates, promotes the draft to config/clients/<id>.yaml, and writes data/clients/<id>/config_approval.json (who, when, SHA-256 of the YAML). It refuses an invalid or unchanged-since-failure draft.
   - The client id must match ^[a-z0-9_]{2,40}$. Uploads are saved only under data/clients/<id>/source/ with a sanitised name.

4. Review workflow (files only, no database). States: draft, in_review, changes_requested, approved. A copy of report.md at submit time is stored under review/versions/. If report.md or metrics.json later changes, the status reads "draft (changed since approval)" and the old approval does not carry over.
